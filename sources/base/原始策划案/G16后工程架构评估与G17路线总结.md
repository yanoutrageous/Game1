\## 一、当前工程总体判断



\### 总体结论：架构基本健康，但顶层导航已到拆分临界点



当前工程最健康的部分是 \*\*局内状态 → 查询快照 → 展示模型 → UI 信号 → CommandBus 命令\*\* 这条链路。Godot 项目 README 已经明确了 `TruthMap`、`IntelMap`、ViewModel 的边界原则：UI 应读取 ViewModel，不直接读取真实地图状态；这和 G15/G16 的 Encounter 展示适配方向一致。(\[GitHub]\[2])



当前最危险的部分不是 Encounter / Combat，而是 \*\*`run\_scene.gd` 正在同时承担运行态、页面态、顶层导航、UI 构建、CommandBus wiring、RunSurface wiring、调试入口、临时主菜单 / 出发 / 长期入口的协调职责\*\*。`run\_scene.gd` 当前约 1048 行，且内部已有 `SCREEN\_MAIN\_MENU`、`SCREEN\_DEPLOY`、`SCREEN\_LONG\_TERM`、`SCREEN\_SETTINGS`、`SCREEN\_RUN` 等顶层页面状态常量，说明“应用壳”已经事实上存在，但还没有被正式抽象出来。(\[GitHub]\[3]) (\[GitHub]\[3])



因此，当前项目具备继续自上而下构筑局外系统的基础，但前提是 \*\*G17 先把顶层导航边界定住\*\*。如果直接在现有 `G9ShellPanel` 和 `run\_scene.gd` 上继续加正式主菜单、出发探索、长期系统，后续返工会显著上升。



\### 当前可继续推进的理由



1\. \*\*G15/G16 没有把局外系统锁死。\*\* `EncounterContract` 明确是 public display / command contract，不拥有规则状态；`EncounterResolver` 是 read-only adapter；`RunQueryFacade` 是 UI / presentation 层读取 run state 的快照边界。(\[GitHub]\[4]) (\[GitHub]\[5]) (\[GitHub]\[6])

2\. \*\*RunSurfaceModel / RunSurface 的方向正确。\*\* `RunSurfaceModel` 从 snapshot 构造显示模型，`RunSurface` 通过 `encounter\_option\_selected` 信号向外发出公共 option payload，而不是直接解析 Encounter 规则。(\[GitHub]\[7]) (\[GitHub]\[8])

3\. \*\*CommandBus 已能承接 G15/G16 additive 命令桥。\*\* `select\_encounter\_option` 对普通搜索、宝箱、事件、Monster attack\_basic 都走统一入口，Monster attack\_basic 再桥到既有 deterministic combat。(\[GitHub]\[9])

4\. \*\*save / meta 目前仍是占位边界，没有造成沉重历史债。\*\* `MetaProgressAdapter` 和 `SaveAdapter` 都明确是 contract-only / placeholder，且 `can\_write\_persistence()` 返回 false；这意味着 G20 仍有机会干净建立 Profile / Meta / Save 骨架。(\[GitHub]\[10]) (\[GitHub]\[11])



\### 当前不应继续堆叠的理由



现有 `G9ShellPanel` 是临时 shell，不应直接演化为正式架构。它已经包含“教学局”“继续标准局”等主菜单低权重入口，而主菜单策划明确要求主菜单不直接开始或继续探索，也不显示“继续上次配置”；正式主菜单应只有固定大入口：出发探索、长期系统、设置、退出游戏。(\[GitHub]\[12]) 



现有 Deploy 临时页也不是最终出发探索结构：代码里的 Deploy tabs 包含 `map / warehouse / claim / config / talents / character`，而策划案要求一级页签稳定为 `地图 / 仓库 / 申领 / 出勤配置 / 作业许可`。(\[GitHub]\[12])

\## 二、G15 / G16 质量判断



\### 1. G15 Encounter 框架判断



\*\*结论：适合作为后续局内模块基础，建议默认冻结 contract 语义，只做 additive 扩展。\*\*



G15 的核心优点是边界清楚：



| 组件                  |    当前判断 | 原因                                                                                                                            |

| ------------------- | ------: | ----------------------------------------------------------------------------------------------------------------------------- |

| `EncounterContract` |      健康 | 明确只定义 display / command contract，不拥有规则状态；适合做 UI、CommandBus、Resolver 之间的公共协议。(\[GitHub]\[4])                                     |

| `EncounterResolver` | 健康但需防膨胀 | 当前是 read-only adapter，从 `RunContext` 构造 public view model，再把真实规则执行交给既有 command path。(\[GitHub]\[5])                             |

| `RunQueryFacade`    | 健康但需控范围 | 已把 `encounter\_view\_model`、`encounter\_result\_summary` 暴露为快照字段；适合作为 UI 查询边界，但不应继续塞入 profile / meta / long-term 数据。(\[GitHub]\[6]) |

| `RunSurfaceModel`   |      健康 | 只消费 snapshot 的 public encounter 字段并构造展示段；这是正确的 display-only adapter。(\[GitHub]\[7])                                             |



G15 最需要防止的不是现有实现问题，而是后续扩展方式错误。不要把以下内容放进 `EncounterContract`：



```text

长期解锁判断

仓库真实库存

抽奖结果

MetaProgress 写入

作业许可完整规则

Profile 成长结算

```



Encounter 应继续只回答：



```text

当前房间对玩家公开呈现什么？

当前公开选项是什么？

玩家选择某个 option 后应该发出什么 command？

执行后如何显示 summary？

```



\### 2. G16 combat / monster encounter foundation 判断



\*\*结论：适合作为“单怪、基础、确定性、attack\_basic”的战斗房基础；不应被误认为完整战斗系统。\*\*



G16 的质量点在于它没有重写战斗结算语义。仓库文档明确说明：Monster rooms 暴露 `monster\_basic / combat\_basic` public encounter data、`attack\_basic` option、monster summary、risk/reward preview、combat result summary，`attack\_basic` 经 `select\_encounter\_option` 路由到既有 deterministic `fight\_current\_enemy` 链路；同时 G16-R3 不改变 `CombatState.fight\_enemy()`、`RoomResolver.fight\_current\_enemy()`、`RunRuleService.apply\_combat\_reward()` 的结算语义。(\[GitHub]\[1])



代码上，`CombatState` 已有 `build\_monster\_summary()`、`build\_combat\_reward\_preview()`、`build\_combat\_risk\_summary()` 等 helper，summary 中包括 monster tags、enemy/player power、reward preview、risk summary、codex placeholder ref 等；这符合“展示辅助，不改变战斗语义”的范围。(\[GitHub]\[13])



G16 当前适合作为：



```text

普通 Monster 房

单怪基础战斗

attack\_basic

确定性风险预览

确定性奖励预览

战斗结果摘要

```



不适合作为：



```text

Boss

elite

多怪

技能 / 被动

实时战斗

action combat

复杂掉落经济

完整战斗动画

完整怪物图鉴

```



仓库状态文档也明确 G16 尚未实现 Boss、elite、多怪、技能、被动、完整掉落经济、MetaProgress、Deploy persistence、完整事件库、完整 gameplay runtime PASS 或 manual playtest PASS。(\[GitHub]\[1])



\### 3. G17 前是否需要修 G15/G16



\*\*不需要阻塞性修正。\*\*



G17 前不应大改 G15/G16。建议只做三类小处理：



1\. \*\*冻结 Encounter contract 的字段语义。\*\* 新字段只 additive，不重命名、不改变 option payload 的基本结构。

2\. \*\*给 `EncounterResolver` 留扩展点。\*\* 后续新房间不要把所有逻辑都塞进一个 `match`；可以后置拆 `EncounterAdapterRegistry`。

3\. \*\*禁止局外系统直接调用 combat helper。\*\* 局外只读 preview / unlock snapshot；不能在 Deploy 或 LongTerm 中调用 `CombatState` 修改 run state。



\### 4. 是否影响主菜单、出发探索、长期系统



\*\*不会形成结构性冲突。\*\*



G15/G16 属于局内 Encounter / Combat foundation；主菜单、出发探索、长期系统属于局外 shell / profile / preparation / projection。只要 G18 的 `RunStartConfig / DeployConfig` 通过一个 RunBootstrapper 创建 run，而不是直接改 `RunContext`，G15/G16 不会阻碍局外系统。

\## 三、当前自上而下路线是否合理



你的路线整体合理，但我建议微调为：



```text

G17：AppShell / NavigationIntent / PageRouter + 最小主菜单 shell

G18：出发探索 / 出勤准备 shell + RunStartConfig / DeployConfig

G19：长期系统 shell / 长期模块入口

G20：长期状态与局外数据骨架 / Profile / Save / UnlockSnapshot

G21：仓库 / 图鉴 / 收藏 / 外观 adapters

G22：抽奖 / 唯一藏品 / 收藏展示

G23：局外-局内 integration audit / SettlementAdapter

G24+：局内内容批量接入

```



你原来的顺序：



```text

主菜单 → 出发探索 → 长期系统 → 局外主要内容 → 抽奖 / 收藏 → 回到局内内容接入

```



原则上成立。原因是三份策划案的职责边界是互相匹配的：



主菜单被定义为“基地门厅 / 中控入口”，不承担资源、任务、出勤、仓库、长期成长、直接开始探索等职责。

出发探索被定义为“本局准备中心”，负责地图、难度、装备、消耗品、补给、服务、作业许可、风险摘要、开始 / 继续探索，但不负责完整长期任务、图鉴、研究、抽奖、外观等深层系统。

长期系统被定义为“记录、解锁、目标、收藏、展示”，且明确不负责本局出勤配置、地图选择、装备配置、直接开始探索或直接修改本局状态。



唯一需要改的是：\*\*不要把 G17 理解为“先画完整主菜单界面”。G17 应先把应用导航骨架立住。\*\*

```text
直接继续探索

```



策划案明确要求资源信息只在对应功能页显示；主菜单只允许通过红点 / 角标表达“有新内容或待处理事项”，不展示具体资源数量。



\### 哪些必须跳转到出发探索



```text

地图选择

难度选择

仓库出勤视角

申领

出勤配置

作业许可

开始探索

继续探索

放弃当前探索

套用上次配置

```



主菜单的“出发探索”按钮即使存在进行中探索，也不改名为“继续探索”；“开始 / 继续”的切换在出发探索页面内部发生。



\### 哪些必须跳转到长期系统



```text

任务

图鉴

成就

研究

回收资历

抽奖

收藏 / 外观

长期记录

长期解锁

```



抽奖不应作为主菜单独立大入口，而应归入长期系统中，与其他长期模块并列。



\### 是否显示资源、任务进度、仓库容量



\*\*不显示。\*\*



可以显示：



```text

红点

新内容角标

未读提示

研究完成提示

图鉴新增提示

仓库新增提示

```



但不显示具体数量。



\### 是否出现“继续探索”



\*\*主菜单不出现。\*\*



存在进行中探索时，主菜单仍显示“出发探索”。进入出发探索后，右侧出勤准备区域 / 主操作按钮再显示“继续探索”。



\### 是否直接启动 RunScene



\*\*不应该。\*\*



主菜单只发：



```text

NavigationIntent(target = "deploy")

```



真正开始探索必须经过：



```text

MainMenuShell

→ NavigationIntent

→ DeployPrepShell

→ DeployConfig / RunStartConfig

→ RunBootstrapper

→ RunScene

```

\## 八、出发探索低耦合边界



\### 是否应生成 RunStartConfig / DeployConfig



\*\*应该，而且这是 G18 的核心。\*\*



出发探索的定位是把局外资产和长期解锁转化为“本局开局条件”。

因此它的主要产物不应该是直接修改 `RunScene`，而应该是一个稳定 DTO：



```text

DeployConfig / RunStartConfig:

\- map\_mode

\- difficulty

\- region\_id

\- seed\_policy

\- selected\_loadout

\- carried\_consumables

\- enabled\_services

\- enabled\_intel\_flags

\- enabled\_work\_permits

\- selected\_commission\_id

\- cosmetic\_snapshot\_id, if needed for visuals only

\- profile\_snapshot\_version

```



\### 是否应直接修改 RunScene



\*\*不应。\*\*



出发探索只决定“出发参数”。真实地图、真实 Boss、真实房间、真实事件、真实宝箱都应在点击开始探索后生成。策划案明确要求出发探索页只能决定地图生成参数，不应提前生成真实地图内容；真实地图内容在开始探索后才生成。



\### 地图、仓库、申领、出勤配置、作业许可如何分层



| 页签   | 负责                                            | 不负责                                | 输出                                   |

| ---- | --------------------------------------------- | ---------------------------------- | ------------------------------------ |

| 地图   | 选择地图模式、难度、区域、基础规则、模糊风险 / 收益、侦察状态              | 不显示真实布局、Boss 位置、撤离点、具体怪物 / 宝箱 / 事件 | `DeployConfig.map\_\*`                 |

| 仓库   | 出勤仓库视角：查看已拥有且可用于出发的装备 / 消耗品 / 特殊物；轻量加入 / 移出本局 | 不做完整仓库整理、批量出售、完整研究 / 图鉴            | `DeployConfig.loadout/items`         |

| 申领   | 后勤可提供的本局补给、服务、情报、基础装备                         | 不显示完整仓库、不做商店完整版                    | `DeployConfig.claims/services/intel` |

| 出勤配置 | 汇总本局实际携带、装备、许可、服务、背包占用、配置预设                   | 不改长期系统，不结算资源成长                     | `DeployConfig.final\_loadout`         |

| 作业许可 | 展示并启用已解锁的本局许可                                 | 不解锁许可；解锁由长期系统 / 研究 / 资历提供          | `DeployConfig.enabled\_permits`       |



\### 进行中探索、继续探索、放弃探索如何避免污染主菜单



做一个独立的：



```text

RunPresenceSnapshot

```



内容只包括：



```text

has\_active\_run

run\_id

map\_summary

hp\_summary

backpack\_summary

progress\_summary

safe\_state

can\_continue

can\_abandon

```



主菜单最多读取：



```text

has\_active\_run

```



用于退出确认提示，不显示详情、不改按钮名、不提供继续。

出发探索读取完整 `RunPresenceSnapshot`，决定右侧按钮显示“开始探索”还是“继续探索”。策划案也明确：有进行中探索时，主操作显示继续探索、显示当前探索摘要、配置修改锁定或弱化、不能直接开始新探索，放弃探索位于出发探索页内部并需要强确认。

\## 九、长期系统低耦合边界



\### 长期系统是否应只管理记录、解锁、目标、收藏、展示



\*\*是。\*\*



长期系统策划案的核心定位就是：



```text

记录、解锁、目标、收藏、展示

```



它不是出勤配置页、不是仓库页、不是局内系统，也不是单纯属性成长页。



\### 是否应直接改局内状态



\*\*不应。\*\*



长期系统可以影响“未来可用选择”，但不能直接改当前 run。长期系统可以跳转到出发探索，但不能直接装备物品、装配出勤配置、选择本局地图或接取本局委托。



正确路径：



```text

LongTermModule

→ Profile / Unlock state

→ UnlockSnapshot

→ DeployPrepShell 可用项变化

→ DeployConfig

→ 新 run 启动

```



错误路径：



```text

LongTermModule

→ 直接修改 RunContext.hp / power / inventory / map / enemy

```



\### 任务、图鉴、成就、研究、回收资历、抽奖、收藏 / 外观是否应拆成独立模块



\*\*应拆成独立模块。\*\*



策划案已明确长期系统包含：



```text

任务

图鉴

成就

研究

回收资历

抽奖

收藏 / 外观

```



并且这些模块是并列关系：图鉴不是收藏页，抽奖不是收藏 / 外观页的子功能，收藏 / 外观不是抽奖页的子功能，研究不是图鉴详情页，任务和成就不同，委托不作为长期系统主要选择入口。



当前代码中的 long-term 临时页只有 `tasks / codex / achievements / profile / research`，还缺抽奖与收藏 / 外观；这说明 G19 可以先做 LongTermShell 模块入口，但 G22 前不应把抽奖和收藏强行塞进现有临时 page。(\[GitHub]\[12])



\### 抽奖是否应继续后置



\*\*应继续后置到 G22。\*\*



原因不是 UI 难，而是持久化风险。长期系统文档明确：抽奖获得、唯一藏品获得、外观获得、收藏记录、奖励领取状态都属于高重要存档内容，获得内容应优先写入存档记录，再展示结果。



当前 save/meta 仍是 placeholder，不写 storage。(\[GitHub]\[10]) (\[GitHub]\[11])

所以抽奖 / 唯一藏品不应早于 G20 的 profile/meta/save skeleton。



\### 长期系统如何向出发探索提供解锁快照



用：



```text

UnlockSnapshot

```



而不是让 LongTerm 直接控制 Deploy。



示例：



```text

UnlockSnapshot:

\- unlocked\_map\_modes

\- unlocked\_difficulties

\- unlocked\_regions

\- unlocked\_permits

\- unlocked\_claim\_items

\- unlocked\_services

\- unlocked\_intel\_features

\- unlocked\_commission\_types

\- unlocked\_deploy\_slots

```



Deploy 页面只消费这个 snapshot，自己决定显示、锁定、禁用、提示原因。LongTerm 不持有 Deploy UI 节点，不写 DeployConfig。

\## 十二、最终结论



\### 1. 当前路线是否合理



\*\*合理。\*\*



“主菜单 → 出发探索 → 长期系统 → 局外主要内容 → 抽奖 / 收藏 → 回到局内内容接入”的方向正确。它符合你三份策划案的职责划分，也符合当前代码已有的 run/display/command 分层。



但路线名称需要更精确：



```text

不是“先做主菜单 UI”

而是“先做 AppShell + PageRouter + 最小主菜单 shell”

```



\### 2. 是否会造成严重返工



\*\*按推荐方式做，不会造成严重返工。\*\*



严重返工只会在以下情况下出现：



```text

继续把主菜单 / Deploy / LongTerm 都堆进 run\_scene.gd

主菜单直接启动 / 继续 RunScene

Deploy 直接修改 RunContext

LongTerm 直接装备、选图、改本局状态

抽奖 / 唯一早于真实 save/profile 骨架

RunQueryFacade 被扩展成全局 Profile 查询门面

CommandBus 被扩展成所有局外系统命令总线

```



\### 3. 最大返工风险是什么



\*\*最大风险是顶层 shell、出发配置、run start、profile/save 被混在 `run\_scene.gd` / `G9ShellPanel` / `CommandBus` 中。\*\*



当前代码已经有临时三页 shell、直接 start standard / tutorial 的 UI 路径、嵌入 run\_scene 的 page switching；这在 G9 阶段可以接受，但不适合作为 G17+ 正式路线。(\[GitHub]\[12]) (\[GitHub]\[3])



\### 4. 最低返工的实现方式是什么



最低返工方式是：



```text

AppShell 负责页面容器。

NavigationIntent 负责导航意图。

PageRouter 负责页面切换。

MainMenuShell 只发导航。

DeployPrepShell 只生成 DeployConfig。

RunBootstrapper 只用 DeployConfig 创建 run。

LongTermShell 只读 / 写 profile，不直接碰 run。

UnlockSnapshot 从 LongTerm/Profile 投影给 Deploy。

RunResultSummary 从 Run 投影给 SettlementAdapter。

SettlementAdapter 写回 Profile / Warehouse / Codex / Collection。

G15/G16 保持局内基础，默认冻结语义。

```



\### 5. 下一阶段最建议做什么



\*\*下一阶段最建议做 G17：最小 AppShell + NavigationIntent + PageRouter + MainMenuShell。\*\*



G17 不要追求完整主菜单美术和全部交互。它的真正目标是把未来所有局外系统的“路由口”定住，防止 G18/G19 开始后每个页面都各自直接碰 `run\_scene.gd`、`CommandBus`、`RunContext`。



一句话结论：



```text

当前 G15/G16 可以保留并冻结为局内 Encounter / Combat 基础；

当前自上而下路线正确；

G17 应先确立 AppShell / NavigationIntent / PageRouter；

最大风险不是 Encounter，而是顶层导航与 Deploy 启动流程继续内聚在 run\_scene.gd；

只要 G18 用 DeployConfig、G20 用 Profile/UnlockSnapshot/SettlementAdapter，后续不会发生严重返工。

```

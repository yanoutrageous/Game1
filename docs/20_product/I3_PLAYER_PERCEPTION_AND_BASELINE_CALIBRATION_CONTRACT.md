# I3 玩家感知闭环、表现架构与 Base 基线校准契约

文档状态：I3 已关闭契约
阶段状态：`CLOSED / PASS_WITH_NOTES`
授权日期：2026-07-23

## 1. 阶段判断

I3 是必要的。I2 已建立可工作的程序、保存、结算和静态界面基线，但其
39 张生产截图只覆盖 13 个静态状态与三个 16:9 分辨率；动态交互手感、
连续玩家路线、最终动画、长局和设备矩阵在 I2 中明确未验收。因此 I2 的
`PASS_WITH_NOTES` 与玩家实际体验未达到预期并不矛盾。

I3 不推翻 I2，也不把项目改成 UE 迁移工程。项目继续处于“增量开发与存量
修改并行”阶段；I3 以 Godot 的领域权威、保存、结算、KnownMap、防泄漏、
固定步长战斗和容量替换规则为底座，重构玩家真正感知到的闭环。

I3 的单一目标是：

> 让生产入口中的每个核心玩家行为形成可感知、可解释、可复现、可回归的
> 完整闭环，并把原始策划与美术整理成不丢信息、可追溯、可消费的仓库内
> Base 基线。

I3.0–I3.7 是同一阶段的内部切片，不得将某个切片的通过表述为 I3 已关闭。

## 3. 事实优先级与对照裁决

1. 当前 Godot 代码、运行时权威快照和真实生产路线优先于旧文档。
2. 原始策划案表达设计意图；若与当前代码冲突，必须登记关系和裁决，不得
   静默把任一方改写成已实现事实。
3. UE 与 Lua 捕获只说明参考体验，不拥有 Godot 的领域、保存、数值、许可或
   架构权威。
4. 文件夹名称（如 `selected`、`game_ready`）不是审核或运行时状态。
5. 同一语义状态缺少真实素材时必须标记 `BLOCKED_MISSING_SEMANTIC_ASSET`；
   禁止以错误状态贴图、色调或缩放替代后再把测试改成通过。

每项体验决策必须属于且只能属于以下一种：

| 决策 | 含义 |
| --- | --- |
| `UE_PARITY` | UE 的玩家感知闭环明确更好；Godot 对齐其信息层级、反馈时序或交互语义 |
| `KEEP_GODOT` | Godot 在权威、防泄漏、可访问性或操作效率上更好；明确保留 |
| `NEW_I3` | 两者都不足；依据当前需求和运行事实建立新的 I3 方案 |

“参考 UE”不等于复制 UI 像素、类结构、DebugSubsystem 或资产文件。

## 4. 先审计、再执行、再审计

每个切片必须按同一顺序完成：

1. **切片前审计**：生产入口、真实消费者、权威字段、玩家路线、UE/Godot
   优劣、素材身份、性能风险、回归面。
2. **允许清单与停止条件**：明确可修改文件、受保护文件、成功标准、回滚点。
3. **执行**：只修改本切片必需内容；不借机改规则、经济、保存或结算权威。
4. **定向验收**：行为、视觉、输入、焦点、减弱动态、三分辨率与污染检查。
5. **完成审计**：验证真实消费者已迁移、旧路径未继续生效、无第二权威、
   未通过项没有被静态截图或占位符掩盖。

切片记录位于 `docs/00_governance/I3_SLICE_GATE_LEDGER.md`。

## 5. 内部切片

### I3.0 范围、来源与可比基线

- 冻结 I2、Godot、UE、`sources.zip` 身份。
- 建立 UE/Godot 同路线对照和 `UE_PARITY / KEEP_GODOT / NEW_I3` 裁决。
- 建立 Base 导入、文档关系、素材谱系和真实旅程终验规则。

### I3.1 地图与小地图

- 小地图是玩家附近的局部上下文视图，不是完整地图按比例缩小。
- 小地图与展开图共享唯一房型、危险、目标、玩家、标记语义。
- Monster、Mine、Event、Exit、Chest 等不得错误合并。
- 保留 KnownMap 防泄漏；选择与执行分离；选择时同步显示大字号摘要。
- 展开图允许 Esc、关闭按钮和点击地图外关闭，并保持键鼠/手柄焦点等价。

### I3.2 搜索、箱子、地面物与物品反馈

- 建立“发现/靠近 → 输入确认 → 搜索过程 → 权威结算 → 揭示 → 稳定查看
  → 拾取或返回”的表现状态机。
- 箱子首次打开后直接呈现内部物品；再次靠近已开箱子仍直接呈现内容。
- 地面物靠近自动显示可拾取内容，但拾取仍走权威命令，不改为自动拾取。
- 世界焦点必须有滞回、驻留和目标锁定；成功反馈不得因实体先销毁而丢失。
- 所有物品表面复用唯一品质、名称、重量和详情描述来源。

### I3.3 HUD、协议、输入、动画与呈现架构

- HUD 优先当前可执行主操作和周围雷险；删除工程状态、raw ID 和重复说明。
- 协议变化必须来自权威事件；UI 不猜测规则或结算。
- 快捷背包、背包、世界物品、替换和结果页使用共享物品表现组件/描述符。
- 消除按键首帧额外位移与连续输入的节奏冲突。
- 角色表现支持可替换外观和动画集；减弱动态保留清晰静态姿态。
- 将可复用旅程和表现职责从 `RunScene` 迁出；只新增薄名称而不减少职责不算完成。

### I3.4 战斗、特殊房、撤离、结果与性能

- 保留 60 Hz 确定性战斗；补全怪物预示/入场、攻击预备、命中、恢复和死亡反馈。
- 战斗房离开必须显式操作；触边不得扣费或离开。
- Event/Mine/Exit 使用玩家信息；撤离靠近显示收益、遗留、目标和确认结果。
- 成功、失败、放弃结果明确说明原因、带回、损失、待保全和保存状态。
- 性能以同机器、同 executable、同 seed、同 workload 的前后分布比较；至少记录
  1/3/5 敌人、弹幕峰值、p50/p95/p99/max、hitch 和长局趋势。

### I3.5 主菜单、出发探索、长期系统与设置

- 修正文案/场景锚点、机械割裂动效、错位反馈和空间转场。
- 地图继续属于出发探索同页双栏；禁止回退成“区域 → 难度”分步页。
- 仓库/申领/目标/摘要按玩家任务重新组织；设置必须真实生效且可持久化。
- 长期系统统一导航、视觉语法、详细说明、天赋树语义和角色档案表现。

### I3.6 Base 原始策划与美术治理

- 将 `sources.zip` 中 25 份 `sources/docs/` 原件导入仓库内
  `sources/base/原始策划案/`；文件名和正文信息完整保留，不删减、不改写。
- 原件可以接受非语义格式检查，但任何编码、换行或标题统一不得改变信息；
  默认导入保持源字节和源 SHA。
- 将 `sources/art/` 与 `sources/draw/` 的非压缩成员按内容 SHA 去重为 Base 美术
  内容库；每个被折叠的原路径保留在别名清单。
- 内嵌 `sources/draw/Art.zip`、`docs_governance` 和旧仓库镜像不重复导入；
  其排除理由、来源路径和 hash 必须登记。
- 每个保留对象记录来源、hash、类型、保留理由、生命周期、许可状态、是否可晋级
  运行时和真实消费者；`pending` 不得因目录名升级为 production。
- 运行时晋级另过 `source → derivative → runtime → consumer → visual validation`
  门；Base 入库本身不代表运行时批准。

### I3.7 综合终验与交付

- 逐切片完成审计、跨切片回归、全量自动化、生产旅程、视觉、无障碍、性能和污染门。
- 在提交后对精确 HEAD 运行最终门；worktree PASS 不能替代 head PASS。
- 最终验证原文、handoff、commit 和远端分支必须指向同一 HEAD。

## 6. 玩家旅程终验

最终体验证据必须从生产 `main.tscn` 或公开生产入口开始，并使用真实输入动作。
允许测试固定随机种子和隔离存档；不允许用以下手段构成最终体验证据：

- 调用私有 UI/场景方法直接打开目标状态；
- 直接写玩家坐标、房间快照、结果面板或运行上下文；
- 用合成 ViewModel 代替生产消费者；
- 把截图生成成功写成视觉或动态手感通过。

至少覆盖：主菜单到出发整备、进入局内、移动、地图展开/关闭、搜索、首次及再次
靠近箱子、地面物、背包满替换、Event、Mine、战斗入场/离开、Exit 预览/取消/确认、
成功/失败/放弃、保存失败重试，以及返回局外。每条旅程记录输入序列、权威状态、
可见反馈、持续时间、焦点/modal 和结果。

静态截图是布局证据；动态截图序列或视频是时序证据；人工观察是手感证据。三者
不能互相冒充。任一范围内动态证据为 `NOT_RUN` 时，不得宣称该体验完成。

## 7. 停止条件

出现以下任一项，当前切片不得通过：

- UI、hover、动画或靠近行为自动发出领域命令；
- KnownMap 泄露未知房间或规则；
- UI 成为掉落、数值、结算、保存或状态机的第二权威；
- 缺失语义素材被错误状态素材伪装；
- 同名不同 hash 未裁决却进入运行时；
- Base 原始策划改名、删减或正文被工程摘要覆盖；
- 去重后无法从任一原路径追到唯一保留对象；
- 受保护 scene/resource/project/import/translation 文件未经专门门被修改或暂存；
- 真实生产路线失败但组件 probe 或静态截图仍被写成阶段 PASS；
- 热路径持续加载资源、职责继续无界堆入 `RunScene`，或性能出现无法解释的回退。

## 8. I3 完成定义

I3 只有同时满足以下条件才能关闭：

1. I3.0–I3.7 的切片前审计、执行、定向验收和完成审计都有可追溯记录。
2. 用户已提出的主菜单、出发探索、长期系统、局内、特殊房和结果问题均有
   `IMPLEMENTED_AND_VERIFIED`、`REJECTED_WITH_EVIDENCE` 或
   `BLOCKED_WITH_OWNER_AND_GATE`，不得静默遗漏。
3. 25 份原始策划完整入库且名称不变；Base 美术按 hash 去重，别名与保留理由完整。
4. 真实生产玩家旅程通过，动态证据不是 `NOT_RUN`。
5. KnownMap、领域、保存、结算、幂等、容量替换、fixed tick 和减弱动态回归通过。
6. 同机性能分布无未解释回退；不能只挑最好一轮。
7. 全量 worktree 门通过；提交后 exact-head 门通过；远端分支包含同一 HEAD。

最终状态允许如实为 `PASS_WITH_NOTES`，但 note 只能是契约明确排除或经证据确认的
非阻塞项；不得用 note 降级本契约中的玩家闭环、Base 完整性或精确 HEAD 要求。

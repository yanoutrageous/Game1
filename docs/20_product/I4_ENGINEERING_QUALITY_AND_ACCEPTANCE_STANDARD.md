# I4 工程质量与生产验收标准

文档状态：`ACTIVE / PRE-PASS NORMATIVE`

标准 ID：`I4-QA-FROZEN-1`

冻结时间：2026-07-30

适用阶段：`I4 / ACTIVE`

## 0. 标准效力

本文件是 I4 在任何 `PRODUCTION_PASS`、阶段关闭、提交和 push 之前必须执行的质量标准。
它补充并收紧
`docs/20_product/I4_PRODUCTION_INTERACTION_CONVERGENCE_CONTRACT.md` 中原本过于概括的
视觉、交互、测试场和既有内容验收条款。

规则：

1. 本标准冻结后，不得因为现有实现难以通过而降低阈值。
2. 历史 ART22–ART25、I2、I3、I3R 的 PASS 只保留历史原义，不自动豁免当前生产内容。
3. 自动 runner 返回 0、截图成功生成、几何探针通过、历史截图通过，都不能单独产生视觉 PASS。
4. 玩家或审查者提供的当前生产反例优先于旧 PASS；反例会重新打开对应页面及其布局等价类。
5. 任何违反本文 `MUST` 的项目都必须为 `FAIL`。不存在“看起来大致可以”的条件通过。
6. `SHOULD` 偏差必须登记为观察项；若它同时损害可读性、信息完整性、任务完成或输入可达性，
   自动升级为 `MUST` 失败。
7. 标准本身必须可判定。只写“清晰”“合理”“无明显问题”“不要太挤”而没有对象、测量和阈值，
   不构成有效验收规则。

## 1. 每条验收规则的完整结构

每条正式规则必须能回答以下八个问题：

| 字段 | 必须回答的内容 |
| --- | --- |
| 对象 | 哪个页面、控件、文本、状态、输入或数据投影被检查 |
| 前置状态 | 分辨率、UI 比例、数据夹具、焦点、模态、动效阶段 |
| 测量 | 使用什么边界、计数、时长、动作序列或语义哈希 |
| 失败阈值 | 从哪一个具体数值或事件开始判定 FAIL |
| 根因 | 失败属于字体度量、固定尺寸、缩放不同步、层级、数据或其他哪类原因 |
| 修复顺序 | 优先扩容、重排、换行、滚动，还是调整纹理安全区 |
| 信息保护 | 哪些信息、命令、状态或实例身份不得因修复被删除 |
| 复验范围 | 修复后重跑当前状态、布局等价类、完整页面还是完整生产旅程 |

缺少任一字段时，该规则只能作为设计建议，不能作为 PASS 依据。

## 2. 判定状态与证据隔离

### 2.1 状态

| 状态 | 精确定义 |
| --- | --- |
| `NOT_RUN` | 尚无本次候选 commit/worktree 的证据 |
| `BLOCKED` | 环境或外部设备缺失，未执行；不能解释为通过 |
| `FAIL` | 至少一个 `MUST` 失败，或证据不完整/不可重现 |
| `TARGETED_PASS` | 单一领域或 runner 通过；不包含真实视觉和完整旅程 |
| `VISUAL_CANDIDATE` | 真实渲染证据已生成且机器门通过，尚未逐图人工判定 |
| `VISUAL_PASS` | 本文件要求的原图已逐图人工复核，所有 `MUST` 通过 |
| `PRODUCTION_PASS` | 自动、真实视觉、动态输入、存档/失败和生产路由同时通过 |
| `STAGE_PASS` | I4 全部硬要求、exact-head/full、审计和远端 SHA 同时成立 |

状态只能按证据升级，不能根据相邻门推断。

### 2.2 证据类别

以下类别必须分别记录，互不替代：

- `AUTO`：领域、投影、保存、几何、焦点和回归 runner。
- `CAP`：真实渲染器原尺寸 PNG 和捕获清单。
- `VIS`：逐张原图人工复核记录。
- `DYN`：真实窗口中的转场、滚动、操作链和连续观察。
- `INPUT`：鼠标、键盘和物理手柄。
- `SAVE`：旧档、隔离、哈希、失败注入和回滚。
- `PERF`：同机同配置的帧时、内存、节点和资源。
- `AUDIO`：实际输出设备、路由、音量和缺失资源。
- `ASSET`：manifest、哈希、尺寸、导入和消费者。
- `FAIL`：失败包与精确复现命令。
- `GIT`：worktree、exact head、远端 SHA 和受保护文件门。

## 3. 几何模型：遮挡、裁切和间距如何判定

### 3.1 边界定义

所有玩家可见控件使用以下边界：

- `R`：控件分配矩形，即 Godot `Control` 的全局逻辑矩形。
- `S`：内容安全矩形，即 `R` 扣除九宫格切片、纹理装饰侵入和显式内容内边距后的区域。
- `G`：字体实际墨迹矩形；不是 Label 节点矩形，也不是估算字符数。
- `V`：可见图形矩形；包括框体、角饰、焦点光和 alpha ≥ 0.25 的装饰像素。
- `H`：输入命中矩形。
- `F`：焦点轮廓矩形。
- `P`：当前 ScrollContainer 或 viewport 的可见裁切矩形。

逻辑画布为 1280×720。所有矩阵先换算到逻辑坐标，再同时检查最终设备像素。
浮点布局只允许 `0.5` 逻辑像素的计算容差；最终截图中任何持续可见的 1 设备像素裁切或交叠
仍按失败处理。

### 3.2 文字遮挡

满足任一条件即为 `VIS-TEXT-OCCLUSION / FAIL`：

1. `G` 的任一部分位于 `S` 外，容差超过 0.5 逻辑像素。
2. `G` 与兄弟控件或装饰的 `V` 中 alpha ≥ 0.25 的像素发生可见交叠。
3. 框体、角饰、滚动条、步进器、徽标或焦点框穿过字形笔画。
4. 上下两行文本的墨迹相交，或行距不足造成重音、标点、数字上下缘不可辨。
5. 文本虽未相交，但连续两个以上字形与其实际承载背景的对比度低于：
   常规正文/按钮 4.5:1，大号文字（字号 ≥22）3:1，disabled 文字 3:1。
6. 动画稳定状态下文字与自己的承载底板不同步，造成文字周期性越过 `S`。

允许的唯一几何例外：

- 同一组合控件内部的共享边框可以相接；
- 装饰可以进入 `R`，但不得进入 `S`；
- tooltip、模态和明确登记的 overlay 可以覆盖背景控件，但必须阻断背景输入，且自身文字仍满足本节。

### 3.3 控件与框体遮挡

满足任一条件即为 `VIS-CONTROL-OCCLUSION / FAIL`：

1. 两个可独立操作的同层兄弟控件 `H` 相交超过 0 逻辑像素。
2. 一个控件的 `V` 遮住另一个控件超过其短边的 5%，即使文字尚未被盖住。
3. 焦点轮廓 `F` 被父容器或相邻控件裁掉任何一边。
4. ScrollContainer 的滚动条覆盖内容 `S`，而内容宽度没有为滚动条预留空间。
5. 模态可见时，背景仍可命中；或模态按钮被底部装饰、遮罩边缘、窗口边缘压住。
6. 收起/展开完成后仍有控件停留在过渡位置，或透明度小于 1 却被当作稳定截图。

### 3.4 最小净距

| 对象 | 最小净距 |
| --- | ---: |
| 紧凑按钮文字墨迹到自身框体内缘 | 4 逻辑像素 |
| 常规按钮/页签文字墨迹到自身框体内缘 | 6 逻辑像素 |
| 正文/详情文字墨迹到承载框体内缘 | 8 逻辑像素 |
| 两个独立紧凑控件可见边框 | 4 逻辑像素 |
| 两个常规控件可见边框 | 8 逻辑像素 |
| 一行摘要卡之间 | 4–8 逻辑像素 |
| 主要工作区到羊皮纸/窗口装饰侵入边缘 | 8 逻辑像素 |
| 焦点轮廓到 viewport 裁切边缘 | 2 逻辑像素 |

步进器 `− 数量 +` 可以使用一个共享框体并让三个分段零间距相接，但必须同时满足：

- 三个 `H` 不相交；
- 分段之间至少有 1 逻辑像素连续分隔线；
- `−`、数量、`+` 各自的 `G` 到分段内缘至少 4 逻辑像素；
- 共享框体不与卡片外框、滚动条或第二行文字相交；
- 鼠标、键盘和手柄焦点都能区分减、增两个动作。

### 3.5 边框带宽与层级

边框宽度不能用纹理文件的透明边距或 StyleBox margin 代替测量。定义：

- `B`：从控件最外侧连续可见边缘，到内部主填充色/纹理连续区域之间的可见边框带宽；
- 外投影、焦点光和角饰单独计入 `V`，不计入 `B`，但仍不得侵入 `S`；
- 分别测量上、下、左、右四边，使用最大值判定；
- 选择态如果叠加第二圈描边，两圈的总宽度计入 `B`。

| 组件级别 | 单边 `B` 上限 | 额外比例门 |
| --- | ---: | --- |
| 页面/羊皮纸最外层主框 | 16 逻辑像素 | 上下或左右合计不超过对应短边的 6% |
| 主要工作区/详情/模态 | 8 逻辑像素 | 对应两边合计不超过短边的 10% |
| 常规卡片、摘要行、页签、按钮 | 4 逻辑像素 | 对应两边合计不超过短边的 14% |
| 紧凑步进器、标签、徽标 | 2 逻辑像素 | 对应两边合计不超过短边的 16% |
| 大型装饰性主操作 | 6 逻辑像素 | 文字 `G` 到 `S` 仍须满足第 3.4 节 |
| 焦点/选中附加描边 | 2 逻辑像素 | 不得推动布局或形成第三层完整框 |

同一内容簇从内容向外追溯父级，最多允许：

1. 一层主要装饰框；
2. 一层功能分组框或细描边。

第三层及以后只能使用背景明度、4–8 px 间距、1 px 分隔线或局部角标，不能再使用完整四边
装饰框。具体规则：

- 羊皮纸已经提供页面主框时，左右工作区可以有一层中等框；其内部卡片只能使用细描边，
  不能再套同等级铜铁九宫格。
- 卡片内的步进器使用一个共享薄框或分隔线，不能给 `−`、数量、`+` 各套完整装饰框。
- 摘要板已经有主框时，摘要行使用薄描边/分隔线；不能形成“主板框 + 行重框 + 文本框”。
- focus/selected 优先复用并改色现有细描边，或增加局部角标；不得在原框外再叠完整粗框。
- 连续列表的相邻卡片可以共享分隔线，但不能通过扩大空隙来假装边框变窄。

满足任一条件即为 `VIS-BORDER-WEIGHT / FAIL`：

- 任一边超过表中绝对上限；
- 边框比例超过表中比例门；
- 同一内容簇出现三层完整四边框；
- 边框带宽大于同组件正文实际字体高度的 50%；
- 选中/焦点状态的最大 `B` 比 normal 状态增加超过 2 逻辑像素；
- 为保留粗边框而压缩 `S`、缩小字号、删信息或增加不必要滚动。

边框过宽的修复顺序：

1. 标出页面主框、分组框、卡片框、状态框的层级，删除同层重复边框；
2. 保留最外层美术身份，将内层完整九宫格改为薄描边、局部角标或分隔线；
3. 将步进器合并为单一共享薄框；
4. 让 selected/focus 改色或替换现有描边，不叠加新描边；
5. 重新校准 slice/content margin，使变窄后的 `S` 增加而不是让纹理拉伸变形；
6. 重跑 normal/hover/focus/selected、12 组矩阵和文字安全区门。

禁止直接非等比压扁边框纹理、裁掉角饰的一半、扩大组件来维持原边框比例，或用低对比度
隐藏过宽问题。

### 3.6 为什么会遮挡：强制根因分类

遮挡问题不得只记录“像素不对”。缺陷必须选择以下根因之一；无法判定时用
`GEO-UNKNOWN`，并保持阻断：

| 根因码 | 典型原因 | 必查项 |
| --- | --- | --- |
| `GEO-FIXED-RECT` | 文案/数量增长，但控件仍用固定宽高 | 极值数字、长文本、换行 |
| `GEO-SCALE-DESYNC` | 字号按 UI 比例增长，控件/间距未同步 | 100/125/150% 的 R/S/G |
| `GEO-NINESLICE-INSET` | 九宫格切片和内容内边距小于真实角饰 | 纹理 alpha、slice、content margin |
| `GEO-FONT-METRIC` | 换字体/回退字体后仍沿用旧度量 | 实际 Font、glyph、line height |
| `GEO-CONTAINER-MIN` | 子节点 minimum size 推挤兄弟或滚动容器 | combined minimum、size flags |
| `GEO-SCROLLBAR` | 未为滚动条预留宽度或嵌套滚动抢占 | scrollbar 宽、scroll ownership |
| `GEO-Z-LAYER` | 装饰/模态/提示层 z-index 或 CanvasLayer 错误 | 层级、mouse filter、clip |
| `GEO-TRANSIENT-CAPTURE` | 在 tween、fade、layout settle 前截图 | tween、alpha、连续稳定帧 |
| `GEO-HITBOX` | 视觉缩小但命中区仍覆盖邻居 | H 与 V 对照 |
| `GEO-COPY-BUDGET` | 文案超过已冻结文本预算 | 实际字符、换行、语义清单 |
| `GEO-DEBUG-OVERLAY` | 诊断层侵入生产关键区域 | overlay dock/collapse/safe zone |
| `GEO-DATA-EXTREME` | 测试只用了短文案、小数字或单条目 | 边界夹具与真实最大值 |
| `VIS-BORDER-ASSET` | 纹理原始边带过厚或 slice 选错 | 可见 B、slice、拉伸/裁切 |
| `VIS-BORDER-NESTING` | 页面、面板、卡片和子控件重复完整框 | 祖先边框层级 |
| `VIS-BORDER-STATE-STACK` | focus/selected 在 normal 外继续叠框 | 各状态 B 与 V |
| `MAP-CELL-SPILL` | 地图子层使用负 offset、无裁切或尺寸大于格子 | 子层 R/V、cell clip、相邻格交集 |
| `MAP-SEMANTIC-STACK` | 房型/玩家/计数/选择共用中心且无分配矩形 | 子层角色、局部 z、语义优先级 |
| `MAP-MODAL-COMPETE` | 展开地图透明，背景 HUD 仍可读或可命中 | content backing、dimmer、mouse filter |
| `WORLD-ANON-COLLISION` | 碰撞只是匿名矩形，不能追溯可见对象 | obstacle id/source/visual key |
| `WORLD-VISUAL-COLLISION-DESYNC` | 对象、状态或贴图消失但碰撞仍在 | 同事务增删、纹理解析、足迹覆盖 |
| `ASSET-NODE-WITHOUT-TEXTURE` | 只因 Sprite/TextureRect 节点存在就隐藏 fallback | texture 非空、尺寸、可见 alpha |
| `ASSET-SILENT-FALLBACK` | 未登记物品静默借用无关贴图且无诊断 | item id/type、resolved key/path、fallback reason |
| `HUD-PROTOCOL-SAFE-RECT` | 协议文案/压力条按固定比例压入真实框边 | 实际 B、S、极值文案和 UI 比例 |
| `HUD-FIXED-EMPTY-BAND` | 空包/少量物品仍保留固定大列表槽 | 内容高度、最后一项、详情和 footer 间距 |
| `RARITY-CHANNEL-OVERRIDE` | focus/失败/危险状态覆盖品质颜色或形状 | normal/focus/blocked 配对与描述器 |

### 3.7 不损耗信息的修复顺序

发现遮挡、裁切或拥挤后，必须按以下顺序尝试；跳级必须在缺陷记录中说明原因：

1. 排除错误捕获状态：等待字体加载、布局稳定、alpha=1、tween 结束。
2. 修正错误的九宫格切片、内容内边距、锚点、层级和滚动条预留。
3. 回收纯装饰空白和无语义占位，不删除玩家信息。
4. 在已分配工作区内增大控件或让同类控件使用内容驱动高度。
5. 对自然语言使用语义完整的换行和重排；标签与值不得错位。
6. 对可枚举列表使用滚动、分页或展开详情，并保证最后一项完全可达。
7. 在同页兄弟区域之间重新分配空间，但不得破坏冻结的 310/12/310 与 198/424 合同，
   除非先修改产品契约并重新审计。
8. 只删除已证明在同一视图中完全重复、且删除后仍能完成同一决策的信息。
9. 文案精简必须保留对象、数量、状态、代价、结果和阻塞原因；不得把具体原因改成“不可用”。
10. 缩小字号是最后手段；不得低于语义 token 基准，不得用整体 Canvas 缩放伪装修复。

禁止：

- 用省略号隐藏价格、数量、条件、失败原因、奖励或实例语义；
- 把信息移到只靠 hover 才能看到的位置；
- 通过删掉可滚动内容让截图“变干净”；
- 把正文缩成 caption；
- 把两个不同动作合并成不可辨认的图标；
- 只移动视觉框体而不修正 `H` 和焦点邻接。

### 3.8 复验范围

| 修改类型 | 最低复验范围 |
| --- | --- |
| 单一文案 fixture | 当前状态 × 12 分辨率/比例矩阵 |
| 共享字体、字号、主题、九宫格或边框层级 | 所有玩家页面的视觉矩阵 |
| 共享卡片/步进器 | 所有消费该组件的页面、数量极值和输入矩阵 |
| ScrollContainer/布局合同 | 当前布局等价类全状态 × 12 矩阵 |
| CanvasLayer/z-index/modal | 全部模态优先级与点击穿透旅程 |
| 生产数据投影 | 对应领域 runner、页面全状态和保存/失败门 |

## 4. 字体和文字栅格标准

### 4.1 字体角色

1. 所有玩家可见中文标题、页签、按钮、卡片名称、说明、详情、状态文案、HUD、tooltip
   和弹窗必须以 `FusionPixel` 为主字体。
2. `display/readable` 仅是字号、行高、换行和信息密度的语义角色；两个角色都必须解析为
   FusionPixel 主字体，不得借角色之名切换成另一套正文视觉。
3. `Noto Sans CJK` 只能作为 FusionPixel 确实缺少字形时的显式 fallback，不得成为任一
   玩家页面、控件类型或中文信息簇的默认主字体。
4. 同一个中文词组、句子、按钮或卡片内不得出现主字体跳变。
5. 同一个信息簇最多使用一种主字体；数字可以使用 display 语义 token，但基线、字重和颜色必须与
   相邻中文一致，不能看成另一套 UI。
6. fallback 不得在同一中文字符串中产生可见字重、宽度或基线跳变。

“信息簇”指同一卡片、同一摘要行、同一按钮组、同一详情头或同一 HUD 组。

### 4.2 字号下限

| 语义 | 100% 基准字号 |
| --- | ---: |
| 页面标题 | 38 |
| 分区标题 | 22 |
| 主操作 | 26 |
| 常规按钮 | 18 |
| 页签 | 17 |
| 正文 | 16 |
| 次要正文 | 14 |
| 说明/caption | 13 |

125% 和 150% 必须请求对应放大字号；布局可以换行或滚动，但不得为了塞入旧固定框而回落到
低于 100% 基准字号。任何控件如果只能通过低于基准字号才能 fit，即为布局 FAIL。

### 4.3 清晰度

FusionPixel 主字体必须使用 `FONT_ANTIALIASING_NONE`、
`SUBPIXEL_POSITIONING_DISABLED`、整数请求字号和整数最终基线；所有生产主题类型均不得
启用隐式系统 fallback。最终像素还必须满足：

- 同一笔画边缘不得出现第二条 alpha ≥0.25、与主边缘平行且连续 3 设备像素以上的影边；
- 同一字号、同一字形中重复横/竖主笔画的厚度差不得超过 1 设备像素；
- 验收 fixture 中“日、目、回、器、8、0”的内部空腔最窄处至少保留 1 个完整背景设备像素；
- 标点、数字小数点和正负号不丢失；
- 文本父节点和字体自身没有叠加的非整数 scale；
- 真实截图按原尺寸 100% 查看时可读，不能依赖放大查看。

常规正文/按钮与实际背景的对比度必须 ≥4.5:1；字号 ≥22 的大号文字必须 ≥3:1。
描边和阴影不能计入字形前景色来抬高对比度。

Noto fallback 允许对实际缺失字形使用灰度抗锯齿，但必须同时满足：FusionPixel 对该字形
确实无覆盖、fallback 路径显式登记、同一 fixture 不产生可见基线跳变。任何整页或整类控件
以 Noto 为主字体均为 FAIL。

### 4.4 行框与换行

- 单行控件的可用高度必须至少为实际字体高度 + 上下各 4 逻辑像素。
- 多行正文每一行的分配高度必须至少为实际字体高度 + 4 逻辑像素。
- 中文必须按字符/词边界换行；数字、实例名、键位和 `当前/上限` 不得从中间拆开。
- 关键按钮默认单行；超过文本预算时优先扩大、换为经产品确认的两行主操作，不得截断。
- 任何自动 fit 都必须报告 requested size、actual size、measured size 和 available size。

## 5. 信息完整性、密度和分栏标准

### 5.1 信息库存

每个页面在验收前必须有一份“信息库存”，逐项标记：

- 玩家在此页要做的决策；
- 完成决策所需的对象、数量、状态、代价、收益、条件和阻塞原因；
- 信息的唯一权威来源；
- 首屏必须可见、滚动可见或详情可见；
- 是否与同屏另一信息完全重复。

没有信息库存的页面不能通过“内容足够”验收。

### 5.2 删除和精简

只有同时满足以下条件才可删除一条信息：

1. 它与同一视图中另一条信息语义完全相同；
2. 删除后玩家仍能在不打开新页面、不 hover 的情况下完成当前决策；
3. 对象、数量、状态、代价、结果和失败原因没有损失；
4. 自动投影测试和动态旅程仍能证明该信息可达；
5. 缺陷记录写明被删除信息及替代位置。

将信息从首屏移到滚动区不算删除，但必须保证滚动提示、焦点、滚轮/方向键和末端可达。

### 5.3 留白和信息密度

“间距过大”按以下标准判定，而不是凭观感：

- 一行摘要的行高必须在 34–46 逻辑像素内；
- 只有实际需要两行语义时才允许 47–64 逻辑像素；
- 单行内容不得占用 65 逻辑像素或以上；
- 摘要行间距为 4–8 逻辑像素；
- 316 逻辑像素高的摘要 viewport 在 100% 时必须显示至少 6 个单行决策项，
  或 5 个单行项加 1 个真实双行项；
- 150% 时首屏必须显示至少 4 个决策项，其余可滚动；
- 空白占位 Panel 必须隐藏并从容器 minimum size 中移除，不能保留空框；
- 列表末尾允许剩余空白，但条目之间不得用大空白代替分组标题或层级。

### 5.4 Deploy 摘要的精确语义

右侧四页不是四个固定框，而是四个可滚动语义列表。

`速览` 首屏按顺序至少包含：

1. 地图名称 + 难度 + 模式/规则组；
2. 当前委托名称 + 核心目标；
3. 已选装备；
4. 已选消耗品总数/种类；
5. 已用容量/上限 + 剩余容量；
6. 可出发状态，或第一条具体阻塞原因。

`携带` 必须包含：

- 每个已携带装备的名称和数量；
- 每组消耗品的名称和 `已携带/持有`；
- 特殊物/藏品若可带入，单独列出；
- 总重量/容量、上限和剩余；
- 空态明确写“未携带”，不能只留空框。

`本局` 必须包含：

- 当前装备实际生效效果；
- 天赋；
- 协议/规则修正；
- 消耗品或补给的本局效果；
- 未生效项目的具体原因，不得把仓库拥有量误放在此页。

`目标` 必须包含：

- 条件；
- 当前进度；
- 奖励；
- 地图/模式适用性；
- 无目标时的明确空态。

同一信息不得在同一页重复。难度如果已合并在地图行，不再占第二个只有“难度”的行。

### 5.5 卡片

普通物品卡固定为两行语义：

1. 名称；名称字体颜色和卡片边框共同表达品质。
2. 自然语言类别 + 当前上下文数量；购买/出售时可加单价。

规则：

- 玩家层不显示 `T1/T2`。
- 同一张卡一次只显示一种数量语义。
- 购买卡显示“本次购买/可购买”，携带卡显示“已携带/持有”，出售卡显示“待出售/可售”。
- 余额、总价、交易后余额不挤入卡片，统一放在动作汇总区。
- 唯一/锁定等不能只靠颜色，必须有自然语言或形状冗余。
- 卡片行高、图标、两行文字和步进器在 12 组矩阵中均满足第 3 节。

## 6. 交互自然度和操作链标准

### 6.1 动作计数

一次鼠标点击、一次确认键、一次方向键移动或一次独立滚轮手势计 1 个动作。
等待动画不计动作；打开一个仅重复信息的页面、详情或二次确认计动作。
长按连续加减可记为 1 个持续动作，但必须可精确停止且结果可见。
“可精确停止”指释放输入后最多再发生 1 个已排队步进，下一渲染提交后数量稳定，且提交前
玩家能看到最终整数值。

### 6.2 关键任务预算

| 任务起点 | 目标 | 最大必要动作 |
| --- | --- | ---: |
| Deploy 仓库卡已经可见 | 携带数量 +1 或 −1 | 1 |
| Deploy 当前页入口 | 找到已知筛选下第一张卡并调整 +1 | 2 |
| 购买卡已经可见 | 选择 N 并原子提交 | 数量调整动作 + 1 次最终确认 |
| 仓库页 | 全选全部可售并提交 | 3：进入批售、全选、最终确认 |
| 已选合法配置 | 确认出发 | 1 |
| 摘要任一页 | 切到另一摘要页 | 1 |
| 长期通知列表 | 到达具体目标卡/详情 | ≤2 |
| 长期目标详情 | 返回原页、原筛选、原滚动、原选中 | 1 |
| 局内聚合物品行 | 使用一个普通实例 | 1 |
| 局内聚合物品行 | 丢弃一个普通实例 | ≤2；唯一/不可逆项必须确认 |

超过预算即为 `UX-CHAIN / FAIL`，除非额外动作承担新的、不可省略的安全决策。
仅重复上一步信息、要求玩家重新定位、打开无新信息详情或重复确认，都不构成安全决策。

“安全决策”只包括：花费不可自动退还的货币、出售/丢弃唯一或锁定实例、放弃当前运行、
覆盖存档或执行调试写命令。普通携带草稿、页签切换、查看详情和使用可重复普通消耗品不属于
需要额外确认的安全决策。

### 6.3 状态反馈

- 每次加减必须在同一信息簇内立即显示新数量、上下限和禁用状态。
- 可撤销草稿不弹确认；不可逆交易只出现一次最终确认。
- 失败必须保留玩家选择并显示具体原因；不得静默归零。
- 快速连点、键盘重复和手柄重复不能双提交。
- Back 恢复历史，不根据默认页重新构造。
- hover 不能修改选择、已读、携带、待售或购买数量。

## 7. 输入、焦点与可访问性

### 7.1 命中区

- 常规可操作控件 `H` 最小为 32×32 逻辑像素。
- 主要操作最小为 104×38；大型主要操作最小为 180×50。
- 可见按钮小于命中区时，扩展 `H` 不得与兄弟 `H` 相交。
- 点击可见框任一点都应命中同一动作；透明角饰不得抢占点击。

### 7.2 焦点

- 每个可操作控件必须有可见焦点，且不依赖颜色单一通道。
- 焦点出现不得改变 `R`、推动兄弟或触发布局重排。
- 方向键邻接必须符合屏幕空间；不得跳入隐藏、disabled 或被模态遮挡的控件。
- 打开模态后焦点进入模态；关闭后精确返回触发控件。
- 滚动到末端时最后一个控件和完整焦点框必须同时可见。
- 页面返回后恢复之前的控件 ID；若该 ID 已不存在，回到同组最近可用项并记录原因。

### 7.3 非颜色冗余

品质、焦点、选中、危险、锁定和 disabled 中任意两种状态必须至少有两种通道不同：
自然语言、边框/形状、图标、明度/颜色。仅改色即为 FAIL。

## 8. 测试场与局内诊断面板标准

### 8.1 生产同源

测试场必须复用：

- 真实 `RunScene`；
- 真实 UI scene/script/theme/font/layout；
- 真实命令总线和领域服务；
- 真实实例 ID、容量、交易和结算边界；
- 与生产相同的渲染器、UI 比例、语言和资源 manifest。

禁止用测试专用简化卡片、测试专用字体、私有方法直接改 UI 文本或手工构造结果页来证明生产通过。

### 8.2 隔离

- 设置入口只在 editor/debug build 可见，release 中节点、焦点路由和快捷键都不可达。
- 只能从主菜单进入。
- 进入后强制切换到 `dev_sandbox`；退出后恢复原 profile。
- 第一个写命令立即显示 `TAINTED`。
- tainted 会话不得向默认档提交任何金币、实例、进度或结算。
- 每个测试前后记录默认档语义哈希；不一致即为 `BLOCKER`。

### 8.3 可见身份

测试场始终显示：

- `DEBUG/TEST`；
- clean/tainted；
- profile；
- scenario；
- seed；
- save target；
- commit 短 SHA。

生产视图复核模式可以收起详细面板，但必须保留一个不覆盖关键内容的测试水印，防止把测试图误认成正式档。

### 8.4 诊断面板几何

- 默认收起；展开必须是显式动作。
- 收起入口不得覆盖生命/协议、交互提示、库存/掉落操作、结果页主操作或模态按钮。
- 展开面板占 viewport 宽度不超过 28%，高度不超过 75%；内容超出时面板自身滚动。
- 展开面板不得改变生产 UI 的锚点和尺寸。
- 展开面板若遮住任一关键控件，必须可移动或换边停靠；默认位置必须零关键遮挡。
- 诊断面板获得焦点时，生产输入暂停；关闭/收起后焦点精确返回。
- 读状态与写命令必须分区；写命令使用危险样式并显示将要修改的对象。

### 8.5 场景目录

每个场景必须有稳定 ID、seed、初始语义哈希、公开启动命令和预期终态。最低覆盖：

- 每种现有房型；
- 普通战斗与峰值战斗；
- 空包、少量、满包；
- 同模板多实例；
- 可使用/可丢弃/唯一锁定物；
- 撤离成功、失败、放弃；
- 保存成功、拒绝写入、写入中断；
- 模态嵌套和焦点恢复；
- 12 组视觉矩阵的 clean 与 panel-expanded 状态。

重置同一 scenario/seed 后，领域语义哈希必须一致。时间戳和动画相位不纳入领域哈希。

### 8.6 失败包

失败包必须包含：

```text
identity.json
scenario.json
actions.json
state_before.json
state_after.json
save_before.json
save_after.json
focus_modal.json
geometry.json
runtime.log
failure.png
reproduce.ps1
```

`failure.png` 必须是失败发生后第一个稳定可见状态，不得只保存下一次成功截图。

## 9. 现有生产内容的验收范围

### 9.1 不得继承历史 PASS

当前生产内容必须使用本标准重新验收。ART22 的固定四行摘要、112 px 卡片等旧结构若已被 I4
替代，必须登记为“被新合同取代”，同时指出新的替代门；不得简单改掉旧测试预期以让它变绿。

每个旧断言只能有三种处置：

1. `STILL_AUTHORITATIVE`：继续通过；
2. `SUPERSEDED_WITH_REPLACEMENT`：写明新需求 ID 和替代 runner/视觉门；
3. `INVALID_WITH_EVIDENCE`：证明它从未描述当前生产权威。

没有处置记录的旧测试失败仍是阻断。

### 9.2 内容普查

最终验收前必须从当前生产 registry/model 生成内容普查，至少包含：

- 主菜单与设置；
- Deploy 5 个一级页及其当前全部筛选/状态；
- Deploy 4 个摘要页；
- 长期系统 6 个模块、25 个生产页面、58 个运行资产；
- 局内 HUD、地图、库存、地面掉落、交互提示和所有房型；
- 暂停/设置/确认/失败等模态；
- 成功、失败、放弃和保存失败结果；
- 测试场 clean/tainted、诊断收起/展开和全部 scenario。

普查每行必须有 `state_id`、公开进入路径、fixture、layout_class、risk_flags 和证据路径。
registry 中存在但无法从公开生产路径或测试场同源路径到达的项目为 FAIL。

### 9.3 状态覆盖

每个布局类必须覆盖：

- normal、hover、focus、pressed、disabled、selected；
- empty、one、overflow、scroll_end；
- 最长合法中文、伪英文、最大合法数字；
- 缺图 fallback；
- success、domain rejection、save rejection；
- reduced motion；
- 页面刷新后 selected ID 存在与消失；
- 快速连续输入。

只有数据不同且 `R/S/G/H/F`、控件树、文本预算和交互完全相同的状态才能归为同一布局等价类。
若无法机器证明等价，则必须逐状态验收。

本标准中的“高风险状态”只指带有以下任一 `risk_flag` 的内容普查行：

```text
long_text
max_numeric
overflow
scroll_end
modal
focus_restore
save_failure
domain_rejection
missing_asset
ui_150
debug_overlay
transition
```

不得由执行者临时缩小这份列表。

### 9.4 分辨率与 UI 比例

硬矩阵：

- 1280×720；
- 1366×768；
- 1600×900；
- 1920×1080；
- UI 100%、125%、150%。

共 12 组。PNG 像素尺寸必须与请求窗口一致；逻辑根因宽高因缩放舍入最多允许 1 设备像素差，
但不得造成边缘裁切。

覆盖策略：

1. 1280×720@100% 对内容普查的每一行全量捕获。
2. 1280×720@150% 对每一布局类及所有长文本/极值/overflow 状态捕获。
3. 其余 10 组对每一布局类、每个主页面和全部高风险状态捕获。
4. 若等价类证明失败，则该类的全部内容行扩展到 12 组。

## 10. 各生产表面的专用门

### 10.1 主菜单和设置

- 所有入口文字使用同一 readable CJK 角色。
- 焦点/hover 不移动按钮或改变命中区。
- 设置应用失败不得显示成功。
- 测试场入口只在 debug/editor 可见，release 焦点序列中也不存在。
- 返回主菜单后恢复触发入口焦点。

### 10.2 Deploy

- 地图页保持 198/424，地图与难度同页。
- 其余页面保持 310/12/310。
- 普通卡遵守两行与单一数量语义。
- 步进器遵守第 3.4 节，卡片外框、文字和步进器无交叠。
- 羊皮纸/工作区/卡片/步进器遵守第 3.5 节；卡片和摘要行不得继续使用重型内框。
- 详情标题、类别、品质、描述、事实和动作均可达；不重复“普通 · 普通”等同义字段。
- 摘要遵守第 5.4 节，不使用四个固定 72 px 空框。
- 详情和摘要可滚动；最后一项完全可见。
- 金币只在购买/出售上下文显示。
- 快速出售为全选/清空/一次原子确认。
- 确认出发使用真实 RunStartConfig；阻塞时显示第一条可操作原因。

### 10.3 长期系统

### 10.4 局内

#### 10.4.1 折叠小地图与展开地图的图层

每个地图格定义 `C` 为分配矩形，`S_cell` 为 `C` 内缩 2 逻辑像素后的安全区。局部层级固定为：

| 局部层 | z | 允许内容 |
| --- | ---: | --- |
| `cell_base` | 0 | 未知/已扫描/已探索底板 |
| `semantic` | 20 | 玩家、房型、旗帜、出口、宝箱、事件或雷险之一 |
| `adjacent_badge` | 30 | 已公开的 0–8 相邻雷险数字 |
| `focus_selection` | 40 | 最多 2 px 的轮廓；不得使用不透明中心填充 |

硬规则：

1. 格子必须开启子内容裁切；任一子层 `V` 必须完全位于 `S_cell`，跨入相邻格的可见像素为
   0。最终截图出现 1 设备像素越格即 `MAP-CELL-SPILL / FAIL`。
2. 有纹理的语义图标不得同时保留 `P/F/C/M` 等中心字母；字母只允许在纹理解析失败的
   显式 fallback 状态出现。
3. 无计数时，语义图标分配矩形为 `S_cell` 再内缩
   `max(3, round(0.10 × min(C.w,C.h)))`。
4. 有计数时，计数方块边长
   `Q = clamp(round(0.30 × min(C.w,C.h)), 12, 18)`，位于 `S_cell` 右下；
   语义图标使用计数方块左上剩余区域，二者分配矩形净距至少 2 px、交集为 0。
5. 计数字形 `G` 到计数方块内缘至少 2 px；计数背景 alpha 不低于 0.85，数字与背景
   对比度至少 4.5:1。
6. focus/selected 只改变第 40 层轮廓或不超过 12% 的整体明度；不得替换语义图标、
   隐藏计数或改变格子 `R/H`。
7. 展开地图的内容承载板 alpha 不低于 0.94；背景 HUD 位于 dimmer 后且
   `mouse_filter=IGNORE`。背景协议、交互提示或房间文字不得穿过地图内容板继续可读，
   也不得响应输入。

验收记录必须逐格导出 `state`、四个局部层的 `R/V/z`、clip 状态和纹理键。前置状态至少为：
未知、已扫描、已探索、旗帜、玩家、雷房、战斗房、宝箱房、事件、出口、计数 0、计数 8、
玩家+计数、focus、selected。折叠/展开两种表面和 12 组矩阵全部执行。

根因按 `MAP-CELL-SPILL`、`MAP-SEMANTIC-STACK`、`MAP-MODAL-COMPETE` 登记。修复顺序为：
先修 clip/负 offset，再分配语义与计数矩形，再固定局部 z，最后调整图标尺寸；不得通过
删除房型、计数、玩家或选择信息使画面变干净。任一共享地图合成修改必须同时复验折叠和展开。

#### 10.4.2 房间阻挡与可见内容一一对应

允许没有独立可见对象的碰撞仅有：房间外边界、当前可见门/闸的门禁矩形，以及已经以
可见预警呈现的瞬时战斗几何。其余静态阻挡必须输出：

```text
obstacle_id
room_key
room_type
source_kind
body_rect
visual_key
visual_footprint_rect
resolved_texture_path
texture_resolved
visual_visible
collision_enabled
```

硬规则：

1. `obstacle_id` 在同一房间状态内唯一且稳定；只返回匿名 `Rect2` 数组为
   `WORLD-ANON-COLLISION / FAIL`。
2. 启用碰撞前必须同时满足：纹理非空、宽高均大于 0、对应 CanvasItem 在树内、
   `visible=true`、最终 alpha ≥0.25。
3. `body_rect` 中心必须位于 `visual_footprint_rect`；两者交集面积除以
   `body_rect` 面积必须 ≥0.90。未登记视觉足迹时不能以整张房间背景矩形冒充覆盖。
4. 对象打开、清除、退场、换房或贴图失效时，视觉与碰撞必须在同一次状态提交中更新；
   任一稳定渲染提交出现“视觉无、碰撞有”即失败。
5. 可选装饰缺图时关闭对应碰撞并记录诊断；宝箱、出口、事件等玩法必需对象缺图时，
   必须显示与 `body_rect` 对齐的高对比 fallback，或在玩家取得控制前以可读原因拒绝房间。
   不得让玩家进入后撞上隐形物。
6. debug 碰撞框只能辅助定位，不能代替生产可见对象，也不能作为对应关系 PASS 证据。

前置矩阵覆盖 Normal、Monster（战斗前/战斗中/清场后）、Chest（关/开/空）、
Event（可用/完成）、Mine（隐藏/触发/解除）、Exit（不可用/可用）及四向门锁定/解锁。
对每个状态以不大于玩家半径一半的采样步长扫描可行走区；每个被拒绝采样必须返回
`obstacle_id`，再反查当前可见对象。未知阻挡数必须为 0。

根因按 `WORLD-ANON-COLLISION` 或 `WORLD-VISUAL-COLLISION-DESYNC` 登记。修复时先建立
来源描述器和纹理门，再绑定状态增删，最后校准足迹；不得简单删除玩法必需对象、扩大通道、
缩小玩家半径或关闭全部碰撞。修改房型公共逻辑后复验全部房型、门、攻击裁切与寻路。

#### 10.4.3 右上协议安全区

协议框的 `S_protocol` 由真实可见边框测量，不使用“框宽百分比”猜测：

```text
safe_inset_each_side = max(measured_B_on_that_side + 6, 14)
S_protocol = R_protocol - safe_inset_each_side
```

标题为 1 行，状态/压力为 1 行，压力条高 6 px。标题到状态净距至少 4 px，状态字形底部到
压力条至少 6 px；`G_title ∪ G_state ∪ V_pressure ⊆ S_protocol`，相互交集为 0。
必须用 `协议 5`、`轻度警戒 · 压力 100/100`、压力 0 和 100、五个协议等级、
normal/warning 颜色和 UI 100/125/150% 测量。不得省略压力、截断状态或缩字号换取通过。

协议可覆盖纯房间装饰，但与门的 `H`、交互提示 `G/V`、模态 `V/H`、诊断入口和玩家关键
状态提示的交集必须为 0。展开地图、库存、地面掉落或暂停模态可见时，协议必须处于其
遮罩之后且不可命中。失败使用 `HUD-PROTOCOL-SAFE-RECT` 或 `GEO-Z-LAYER`；先修真实
安全内边距和行布局，再修层级/停用输入，最后才允许调整协议框尺寸。复验所有 HUD 模态组合。

#### 10.4.4 左下物品簇的内容驱动密度

左下物品簇按 `标题 → 列表/空态 → 当前详情 → 负重` 排列。100% UI 下：

| 对象 | 高度/间距 |
| --- | ---: |
| 单物品行 | 44–52 px |
| 相邻物品行 | 4 px |
| 空包状态 | 44–56 px |
| 列表/空态到详情 | 4–8 px |
| 当前详情 | 44–56 px |
| 详情到负重 | 4–8 px |
| 负重行 | 24–30 px |
| 内容到承载框底部 | 8 px |

0 件时不得保留可容纳多行的空 ScrollContainer；1–3 行时列表 viewport 高度等于实际内容
高度，最后一行到详情的空白不得超过 8 px；超过 3 行时才启用滚动，viewport 显示完整
3 行且最后一项可达。任意两个语义相邻对象之间出现连续空白带 >8 px，或承载框在负重行后
保留 >16 px 无语义内部空白，即 `HUD-FIXED-EMPTY-BAND / FAIL`。

修复顺序为内容计数驱动高度、收起空列表、详情紧跟列表、固定负重 footer、最后才调整外框；
不得删除详情、负重、滚动可达项或把信息移到 hover-only。复验 0/1/3/4/满包、长名称、
多品质、滚动末端、1280×720@150% 和全部 12 组布局矩阵。

I4 的 Godot 品质色值冻结如下。它只借用 UE 的色值层级，不继承 UE 布局、控件或数据：

| 规范键 | 自然语言 | sRGB |
| --- | --- | --- |
| `tier_1` | 普通 | `#D0D8E0` |
| `tier_2` | 优良 | `#78DCAA` |
| `tier_3` | 稀有 | `#5FA5FF` |
| `tier_4` | 珍贵 | `#BE78FF` |
| `tier_5` | 传奇 | `#FFC346` |

颜色不是唯一通道：焦点详情或常驻详情必须提供自然语言品质；unique/unknown 必须分别有

#### 10.4.6 物品纹理与地面掉落

每次解析必须记录：

```text
item_id
item_type
requested_visual_key
resolved_visual_key
resolved_texture_path
texture_size
explicit_mapping
fallback_used
fallback_reason
consumer
```

当前 registry 中的正式物品必须有显式映射；运行时扩展物品可以按已登记 `item_type` 使用
类别 fallback，但必须记录原因。背包快捷列、库存、地面列表、世界掉落和结果对同一物品
必须得到同一 `resolved_visual_key/path`。纹理必须非空、宽高 >0；正式内容的空纹理数为 0。

`ArtVisual`/`TextureRect` 节点存在不等于纹理存在。纹理为空时不得隐藏 fallback；生产
fallback 至少包含非透明类别图形和品质边/光束，debug 诊断同时记录缺失键。世界掉落的
`ArtVisual.texture`、品质光束和可交互上下文必须在同一稳定状态可见；只剩光束而物品本体
为空也为失败。纹理缺失不得保留与该物体绑定的隐形碰撞。

验收必须枚举当前全部 item ID，逐一检查五个消费者；另注入一个不存在的显式路径和一个
未知 item ID，证明前者产生可见 fallback+诊断、后者按类别 fallback 且不崩溃。失败按
`ASSET-NODE-WITHOUT-TEXTURE` 或 `ASSET-SILENT-FALLBACK`。修复顺序为映射、资源存在/尺寸、
共享 resolver、可见 fallback、消费者绑定；不得用一张无关贴图静默覆盖全部缺失。

## 11. 真实渲染捕获与人工视觉复核

### 11.1 捕获环境

- 使用真实 Windows 渲染窗口或等价真实 GPU 渲染器；headless 不能生成视觉 PASS。
- 记录 Godot 版本、renderer、GPU、OS、窗口尺寸、UI 比例、locale、scenario、seed、commit/tree。
- 捕获前必须满足：字体已加载、layout 已稳定、所有目标控件 alpha=1、无未结束 tween、
  滚动位置稳定、焦点为预期控件。
- 稳定条件至少连续 3 个渲染提交保持控件树、关键 `R/S/G/H/F` 与语义状态一致；
  这 3 次不是固定等待，而是稳定性判定。
- PNG 使用原尺寸、无缩放、无有损压缩、无后处理锐化。

### 11.2 自动捕获门

机器必须验证：

- 请求状态数与生成文件数一致；
- PNG 尺寸正确；
- 文件非空、可解码；
- identity 与 manifest 完整；
- 所谓不同语义状态若像素哈希完全相同，必须调查；
- geometry 报告无越界、交叠和不可达滚动；
- 捕获进程退出码和明确 marker 均成功。

通过本节后状态只能是 `VISUAL_CANDIDATE`。

### 11.3 人工逐图流程

每张图必须：

1. 按原尺寸 100% 查看整屏；
2. 查看文字/框体、卡片/步进器、滚动边缘和焦点的局部原像素；
3. 与同一状态的 100/125/150% 并排比较；
4. 与 normal/focus/disabled/overflow 配对比较；
5. 按本文规则逐项记录 PASS/FAIL；
6. 对失败记录屏幕矩形、规则 ID、严重度、根因码和复验范围。

联系表只能用于导航，不能替代原图逐张检查。

### 11.4 动态复核

真实窗口必须另外验证：

- hover、pressed、focus 和 disabled 的转换；
- 滚轮、拖条、方向键和末端滚动；
- 收起/展开和页面切换稳定终态；
- 20 秒常规 UI 动效；
- 60 秒局内 HUD/战斗/掉落动效；
- reduced motion；
- 快速连点和 latest-request-wins；
- 诊断面板展开/收起与焦点归还。

截图不能替代本节。

## 12. 存档、失败和复现标准

- sandbox 前后默认 profile 语义哈希必须完全一致。
- 至少覆盖最新存档、I2 闭合基线旧档、缺字段旧档、损坏档和 future schema 拒绝。
- 购买、出售、使用、丢弃、领取和结算都要有保存失败注入。
- 原子操作失败后，金币、实例集合、数量投影、UI 选择和磁盘内容全部恢复。
- 重试只能产生一次结果；重复回调、快速确认和进程重启不得重复结算。
- 关键 scenario 连续通过 10 次，其中至少 3 次来自新 Godot 进程。
- 完整局外生产旅程连续通过 3 次。
- 任一中途失败将该门连续计数归零，失败证据不得删除。

### 12.1 验证存储收口

C/E 盘清理是 I4.8 的收口门，不是任意释放空间的授权。执行前必须生成精确绝对路径清单，
逐项目记录 `path/type/bytes/rebuildable/retention_reason/disposition`，并遵守：

- 必须保留最终 worktree 与 exact-head 报告、清单、日志、原图、失败反例、失败包、远端
  SHA 证明、命名 stash、用户存档、原始来源包、Base/CAS 索引和恢复证明；
- 先使用已有归档、校验和事务裁剪工具；只有工具没有覆盖且目标明确属于本轮可重建产物时，
  才允许以原生 PowerShell 对单个已解析目录执行删除；
- 不得以盘符、用户目录、仓库根、`.tmp` 根或通配符作为递归删除目标；
- 删除前后分别复量目标和所在盘可用空间；记录实际回收字节、未删除原因和是否可恢复；
- 字体错误、失败验证或中断运行只有在 disposition 与仍保留的反例/日志绑定后才能删除重复
  大文件；不得为节省空间抹去导致修复的唯一证据；
- C 盘只处理已证明由本任务创建、可重建且不被其他任务/应用占用的临时项；不能把系统临时
  目录整体视为项目缓存。

任一来源、用户数据、未绑定失败证据或最终候选证据被误删，均为 `BLOCKER`。仅列出预计
空间、未实际复量，或只报告盘符可用量而没有目标清单，不能通过本门。

## 13. 性能、音频和设备边界

### 13.1 性能

性能只在同机、同 renderer、同分辨率、同 UI 比例、同 seed、同资源和同诊断开销下比较。

最低场景：

- 主菜单、Deploy、长期系统各静置 60 秒；
- 页面往返 20 次；
- 摘要/详情/长列表滚动到末端 10 次；
- 战斗 1/3/5 敌人和峰值弹幕各 60 秒；
- 空包/满包/多掉落；
- 保存成功与拒绝写入。

硬结构门：

- orphan 始终为 0；
- 重复页面往返后 Node 中位数漂移 ≤64；
- Resource 中位数增长 ≤8；
- 稳态前后 10 秒静态内存中位数增长 ≤2 MiB；
- 不发生单次输入导致的重复页面实例或隐藏页持续 process。

真实 GPU 帧时必须记录 P50/P95/P99/max；目标设备和绝对 FPS 未登记时保持 `MEASURED_NOT_ACCEPTED`，
不得用 headless `TIME_FPS` 宣称通过。

### 13.2 音频

必须实际检查主操作、交易成功/失败、出发、局内交互、模态、结果和诊断写命令的音频路由。
缺失、重复播放、音量设置无效、静音穿透或失败播放成功音均为 FAIL。

### 13.3 物理手柄

模拟 InputEvent 只能产生定向证据。物理手柄必须记录设备名、连接方式和完整关键任务结果；
未执行时为 `BLOCKED/NOT_RUN`，不能写 PASS。

## 14. 缺陷严重度与一票否决

| 等级 | 定义 | 示例 |
| --- | --- | --- |
| `BLOCKER` | 数据、存档、交易、调试隔离、崩溃或审计完整性破坏 | 默认档污染、部分扣款、protected metadata 混入 |
| `P1` | 主任务不可完成、信息错误/不可读、输入不可达或界面发生任一可见遮挡 | 字被框盖住、主按钮不可点、摘要缺阻塞原因 |
| `P2` | 任务可完成但违反一致性、密度、字体或冗余规则 | 中文字体混用、72 px 单行空框、重复品质 |
| `P3` | 不违反任何 MUST 的非阻断审美建议 | 可选装饰微调 |

所有 `MUST` 失败都阻止 PASS，严重度只决定修复优先级，不提供豁免。

以下情况直接停止当轮验收：

- 当前真实截图出现任何 P1/BLOCKER；
- 同一共享组件出现 2 个或以上 P2，说明布局等价类未稳定；
- 默认档哈希变化；
- 原子交易部分成功；
- 关键状态使用固定帧等待伪造；
- 捕获时仍处于过渡/透明状态；
- 旧失败测试没有处置就被删除或改成通过；
- 未经登记修改 `project.godot`、scene、resource、`.uid`、`.translation` 或 import metadata。

## 16. I4 通过顺序

任何顺序跳跃都不能产生 PASS：

1. `G0 标准门`：本标准、需求矩阵、旧测试处置规则冻结。
2. `G1 内容普查门`：生产页面、状态、资产和布局等价类完整。
3. `G2 领域/保存门`：权威、原子性、隔离、失败和旧档。
4. `G3 静态几何门`：R/S/G/V/H/F、文本预算、滚动和焦点。
5. `G4 真实捕获门`：12 组新鲜原图和完整 manifest。
6. `G5 人工视觉门`：逐张原图判定，零开放 MUST 失败。
7. `G6 动态旅程门`：操作链、动效、滚动、输入和诊断面板。
8. `G7 重复/性能/设备门`：10 连过、3 旅程、GPU、音频、物理手柄分别记录。
9. `G8 worktree/full`：完整回归和 dirty/metadata 审计。
10. `G9 exact-head/full`：候选提交后的同一对象复验。
11. `G10 push`：远端分支 SHA 与本地候选 SHA 完全一致。
12. `G11 storage closeout`：最终证据绑定后按第 12.1 节清理并复量 C/E 盘。

任一后续门通过都不能覆盖前序门失败。修复共享字体、主题、布局、输入或保存代码后，按第 3.8 节
回退到相应最早门重新执行。

# I2 Refactor Direction and Incremental Baseline Contract

文档状态：I2 当前产品/交付契约；阶段 `ACTIVE`，实现尚未声明。
最后更新：2026-07-22

## 1. 阶段目标

I2 将已有工程能力转换为稳定、可理解、可扩展的玩家体验基线。阶段完成后，后续新增与修改应能：

- 从明确的权威接口接入，不绕开状态机、资产账本、结算或保存边界；
- 通过短循环快速看到生产页面效果，并能复现、对比和回归；
- 使用清楚的键鼠/手柄/焦点操作说明完成目标流程；
- 以自动化、静态图、动态人工、真实工作负载性能和失败路径证据分别验收；
- 继续允许增量开发与存量修改并行，而不重新进入无边界核心重写。

I2 是工程侧到玩家体验侧的一次完整重构阶段，但不是全面推倒重写。它只有一个阶段状态和一次最终综合验收；内部切片仅用于控制风险、回归与评审，不能各自冒充 I2 完成。

## 2. 阶段判断

I1 已证明项目拥有真实玩法闭环、统一 runner、隔离生产预览以及程序权威/保存/结算基线，因此从“核心能力集中开发”转为“新增能力与存量修改并行”是正确方向。

这项判断不等于进入维护期。I2 仍需处理高风险的交互架构、玩家信息表达、动效状态、真实设置、素材替换接口和战斗房工作负载；跨进程恢复、完整经济、最终音频、导出与发布也仍不属于既有完成事实。

## 3. 权威与参考冻结

```text
active_repo = git rev-parse --show-toplevel
implementation_target = <active_repo>/Godot/GraytailGodot
engine_target = Godot 4.6 feature target
read_only_reference = E:\UE\Game\UE\Graytail
```

- 当前 Godot 代码、运行数据和可复现实验是实现事实源。
- 仓库文档说明需求、边界和历史，但不能覆盖当前代码事实。
- UE 只借鉴语义、交互节奏和视觉概念，不移植 UE 架构、Debug 权威、固定像素烤字布局或未知许可素材。
- 本机已验证的 I1 runner 使用 Godot 4.6.3；`E:\UE` 是 UE 参考环境，不是当前 Godot 可执行文件的路径权威。
- 历史绝对路径不能用于选择活动仓库或主动导入 source pack。

## 4. 冻结的产品约束

### 4.1 主菜单

- 文字、场景、角色和环境表现必须形成同一空间关系，不能继续以浮在场景上的工程标签为主要表达。
- 转场按入口语义设计：出发探索以角色进入洞口为首选方向；长期系统以画面向下移动进入下层空间为首选方向；其他入口需要自己的合理转场。
- 转场必须有取消/失败/焦点恢复和 reduced-motion 静态替代，不得让动画计时器拥有页面状态权威。
- 角色动画先评估离线 rig-assisted/baked pixel frame 流程与素材替换接口；本契约不承诺运行时骨骼生成。
- 设置不得保留无效控件。展示的每个设置必须对应真实运行行为、持久化语义、默认值和失败反馈；具体字段在设置切片门内冻结。

### 4.2 出发探索

- 页面保持左侧角色、中央核心工作区、右侧摘要的总结构；中央核心改为“左侧选择 + 右侧详情”。
- 右上角常驻当前金币，并来自局外权威快照。
- 地图永远位于同一 Deploy 页面的地图页签：左侧显示地图名称与比例/规模，右侧显示难度和详细信息。禁止引入“区域 → 难度”分步页或离开 Deploy 的独立地图路由。
- 保留现有地图 ID；7×7、10×10、13×13 只作显示分组，不改写标识或存档：

| 显示规模 | 现有 ID |
| --- | --- |
| 7×7 | `classic_7x7_simple`, `classic_7x7_normal` |
| 10×10 | `classic_10x10_easy`, `classic_10x10_standard`, `classic_10x10_hard` |
| 13×13 | `classic_13x13_normal`, `classic_13x13_hard`, `classic_13x13_hell` |

- 仓库用左右布局表达“拥有、当前使用/出勤、品质与操作”。已有单件出勤、使用或出售能力必须接真实命令；快捷/批量售卖属于新增经济规则，在价格、确认、失败、幂等和持久化门通过前不得做成假按钮。
- 申领复用布局骨架，但按购买/领取/条件/库存语义特化，不能仅复制仓库文案。
- 当前出勤配置基于真实 `RunStartConfig`，不能因名称难懂直接删除。先把其真实作用、限制和结果显示清楚；若最终合并/移除页签，必须证明功能有新的可发现落点。
- 目标入口必须区分“本局委托”和局外成就/等级任务/记录。最终页签分类由产品门冻结，不能混用同一“目标”标签遮蔽不同生命周期。
- 右侧摘要删除“当前选择”“路线/难度”“运行状态”等工程式说明，四个二级页签都以可扫描的真实内容为主；顶层应为“概览 / 配置 / 效果 / 目标”，其中效果表示本局附加效果，风险仅作上下文信息，不再占顶层页签。

### 4.3 长期系统

- 复用一致的全局导航/返回语言，重新设计顶部标识、左下收起档案和各模块布局；复用不等于复制 Deploy 的业务结构。
- 模块必须按自己的信息类型提供详情、进度、条件、奖励、状态和可执行操作，不再统一压成少量通用卡片。
- “天赋树”是明确方向，但当前“目标”承载真实任务、成就和委托记录。实施顺序必须是：先确定任务档案的新落点与数据生命周期，再建立天赋权威和布局，最后修改导航；禁止只把“目标”改名为“天赋树”。
- 角色与角色档案应共享可替换角色表现接口，并提高身份、状态、成长、外观和记录的可读性；不在本契约中虚构尚无数据的属性。

### 4.4 局内、房间与结算

- 局内界面必须以实际运行状态为内容源。箱子、门、掉落、协议、地图、背包和结算的视觉不能先于或偏离权威状态。
- 箱子首次打开显示内部物品，之后靠近自动展开内容；地面掉落靠近自动显示可拾取物，但绝不自动拾取。动画完成不能提交奖励。
- 物品使用品质文字/图标/边框/颜色的冗余语义；快捷背包按实际内容绘制并可滚动，不绘制无意义空槽和空边缘；负重放在下中区域。
- 小地图/全图、邻雷数、协议、提示、模态、悬浮详情、边框层级、成功/失败结果和四类特殊房要求逐条以追踪矩阵为准。
- 战斗房离开必须是明确的特殊操作/确认，不得因角色接触边缘直接离开。怪物入场、雷房和撤离提示必须提供多通道反馈，并尊重 reduced motion。

## 5. I1 不变量

I2 所有切片必须继承：

1. `RunStateMachine` 是局内 phase 的唯一写入者；兼容入口只能委托状态机。
2. `RunAssetLedger` 是局内物品位置权威；UI 不能建立第二份可提交库存。
3. `RunRuntimeController`/meta adapter 协调 terminal settlement 单次提交；pending failure salvage 在玩家确认前不写局外。
4. 同一 `result_id` 不重复提交，失败/保存错误必须可解释和可重试。
5. `SaveAdapter` 的临时写入、flush、解析、备份、替换后复验、恢复和未来 schema 保护不得降级。
6. `ContentDB` 仍是生产内容权威；可复用脚本通过既有访问边界取数。
7. UI、动画和计时器不拥有领域决策权；路由提交、奖励、消耗和结算只来自对应权威。
8. 当前进程继续不等于跨进程 active-run 恢复，不得改变声明口径。

## 6. 来源、素材和生成门

优先顺序如下：

1. 当前 Godot 中已登记、已许可、已接线的素材和可替换接口；
2. 当前 Godot 中存在但尚未接线的已审计素材；
3. UE 和本地素材作为只读参考，经 hash/source/license/runtime-key/import gate 后选择性导入；
4. 只有确认现有来源不足，且生成需求、风格、分层、许可证和确定性登记已批准时，才生成新素材。

`.uasset`、烤字固定页面、过程视频帧和未知许可音频/图片不能直接进入 Godot。任何新绑定必须登记来源、许可证、用途、目标路径、runtime key、替换状态和确定性要求。受保护 `project.godot`、场景、资源、`.uid`、`.translation` 与 import metadata 没有专门 gate 时禁止暂存。

## 7. 切片结构

| Slice | 目标 | 关键门 |
| --- | --- | --- |
| I2.0 | 契约、评估、矩阵、架构、验证计划、门账与入口 | docs-only；不得宣称运行时实现 |
| I2.1 | 共享导航/转场、设置、焦点/输入、动效与角色表现基础 | state ownership、persistence、reduced motion、character swap proof |
| I2.2 | 主菜单空间/文字/动效与语义转场 | production preview + dynamic manual review |
| I2.3 | Deploy 信息架构、地图同页、仓库/申领/委托/摘要 | map no-regression、economy command gate、three-resolution interaction |
| I2.4 | 长期系统布局、任务档案迁移、天赋与角色档案 | data-duty migration before rename、module-specific evidence |
| I2.5 | 局内 HUD、地图、背包、箱子/掉落与模态 | authority characterization、input/focus、proximity and no-auto-pickup |
| I2.6 | 战斗/特殊房、结算解释和真实工作负载性能 | deterministic gameplay regression + frame workload + failure paths |
| I2.7 | 跨页面整合、操作说明、全量回归和单一阶段验收 | full/worktree then exact full/head + visual/manual/perf/source evidence |

切片编号是风险控制工具，不是并行的独立阶段。实际实施可以在审计后调整顺序，但不得跳过依赖或以未验证占位代替真实行为。

## 8. 每切片完成门

每个切片至少需要：

- 范围/风险复核，明确 allowed、forbidden、protected paths 和回退点；
- 变更前 characterization，尤其是路由、保存、结算、地图、物品与战斗；
- 与风险相符的 I1 quick/core/ui/full 回归，并为新增行为增加最小可复现 runner；
- 生产场景预览；玩家可见变更还需人工动态、输入/焦点、文案与失败路径复核；
- 资源变更的 source/license/hash/manifest/import/determinism gate；
- `git diff --check`、dirty/staged/metadata 清单和声明审查；
- 只声明实际验证范围，未运行项保持 `NOT_RUN`。

## 9. I2 综合完成定义

只有同时满足下列条件，I2 才可进入单一 closeout：

1. 追踪矩阵每项均有 `implemented / rejected_with_evidence / explicitly_deferred` 处置，不允许静默遗漏。
2. 主菜单、Deploy、长期、局内、特殊房和结果页通过生产路径的静态与动态验收；用户能按操作说明完成关键流程。
3. 键鼠与手柄/焦点、reduced motion、颜色冗余、长文本/本地化和生命周期/保存失败均有明确证据或书面排除。
4. 战斗房性能用真实工作负载测量并给出前后可比数据；refresh 微基准只能作为分项指标。
5. 所有来源/许可/import/metadata 门通过，无未知 dirty 被吸收。
6. 全量 worktree 回归通过；提交后 exact HEAD 全量回归通过；自动化、视觉、人工、性能、CI、导出/发布分别声明。
7. 更新 current state、capability、validation 和 handoff 后才可关闭。I2.0 不创建 validation/handoff，也不提升任何运行能力。

## 10. 非目标

- 全量重写 Godot 项目或迁移到 UE。
- 以 UE 的页面结构覆盖 Godot 当前产品约束。
- 在无规则/数据/命令的情况下制作看似可用的按钮或天赋树。
- 将动画、截图、微基准或文档当成玩法/性能/发布完成。
- 自动解决跨进程 active-run 恢复、完整经济、全量内容、最终音频、导出或发布；除非后续 I2 切片获得明确扩展授权并通过专门门。

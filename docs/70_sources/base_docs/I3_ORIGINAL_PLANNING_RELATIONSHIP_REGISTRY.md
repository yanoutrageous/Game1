## 规则

本表只增加外部关系与当前使用说明，不修改原件。`supersedes`、`patches`、
`extends`、`conflicts`、`historical_input` 描述策划之间的关系，不自动证明规则已
实现。当前 Godot 代码、权威快照和真实运行结果仍是实现事实。

## 冲突处理

1. 同一规则在 v0.1 与 v0.2 冲突时，只在修正文档明确修正的范围内采用 v0.2；
   未修正内容继续追溯到 v0.1。
2. 早期数值/文案与 M5 冲突时，M5 是策划裁决层；若当前代码已经不同，则记录
   `code_divergence` 并由当前阶段决定是否修改，不能改写原件。
3. 长期系统三份文档是“基础界面 → 资产整合 → 内容补全”的组合关系，不以文件日期
   粗暴删除前两份。
4. 独立地图、局内流程、房间类型和 Rule/Modifier 文档相互扩展；任何单份都不能
   单独替代完整局内规则。
5. 历史报告、可行性计算和路线总结保留其假设与时间点，但不得引用其中固定盘符或
   旧 commit 作为当前执行指令。

## 完整性门

- 原件数必须为 25，且每个仓库文件名与 zip member basename 完全一致。
- 每个文件 SHA 必须与 `ORIGINAL_PLANNING_MANIFEST.csv` 一致。
- 任何格式统一都必须证明信息等价；默认策略是保持源字节。
- 工程摘要只能引用原件，不能替换原件或减少信息。
